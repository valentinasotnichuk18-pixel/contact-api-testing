# Підхід до тестування

## Що я виділила зі специфікації

Обовʼязкові поля: Code, MobilePhone
Необовʼязкові поля: Name, Email, BirthDate, GenderCode
Тип полів: усі рядкові, крім BirthDate, який має тип Date
Довідник статі: 0 жіночий, 1 чоловічий

Обидва обовʼязкові поля є ідентифікаторами, але в різних площинах. Code ідентифікує клієнта в зовнішній системі замовника, MobilePhone фактично ідентифікує людину всередині CRM. Тому перевірка унікальності потрібна для обох полів, а не тільки для Code.

## Ізоляція тестових даних

Це головна вимога до набору. Кейси не мають впливати одне на одного через стан бази.

Правила, за якими побудований набір:

1. Кожен кейс використовує власні унікальні значення Code і MobilePhone. Однакові ідентифікатори в різних кейсах призвели б до того, що кейс падав би через дані, залишені попереднім кейсом, а не через дефект продукту.
2. Кожен кейс, який успішно створює запис, має постумову: створений запис видаляється з бази після перевірки.
3. Якщо кейсу потрібен уже існуючий контакт, цей контакт створюється в передумовах самого кейса, а не запозичується в іншого кейса. Формулювання виду «спочатку виконати кейс 1» у наборі не використовується.
4. Наслідок цих трьох правил: набір можна прогнати повторно і отримати той самий результат, а будь-який кейс можна запустити окремо.

## Схема нумерації тестових даних

| Діапазон | Призначення |
|---|---|
| Code CT-0xx, MobilePhone +38067111xxxx | Дані, які створює сам кейс |
| Code CT-9xx, MobilePhone +38067199xxxx | Підготовчі дані, створені в передумовах |

Усі дані синтетичні. Реальні імена, телефони і адреси пошти не використовуються.

## Пріоритети

| Позначка | Значення |
|---|---|
| P1 | Критичний. Стосується основного сценарію створення або цілісності даних у базі |
| P2 | Важливий. Стосується валідації окремих необовʼязкових полів і мапінгу |

## Рівні перевірки

Кожен кейс перевіряється на двох рівнях:

1. Відповідь API: код відповіді і тіло відповіді.
2. Фактичний стан у системі: чи створено запис, і чи всі значення потрапили у поля згідно мапінгу.

Друга перевірка обовʼязкова. Успішна відповідь API без фактичного запису в базі є дефектом, так само як і створений запис у відповідь на запит, який мав бути відхилений.

## Обмеження

Конкретні коди відповіді у очікуваних результатах не вказані, бо їх немає у специфікації. Замість цього вказано очікувану поведінку: успішне створення або відхилення запиту. Питання про коди винесено окремо.
